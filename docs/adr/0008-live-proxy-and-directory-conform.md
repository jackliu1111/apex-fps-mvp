# 独立实时伴随模式、限时流畅代理与目录原片升格

在不引入任何服务端、插件或录屏软件绑定的前提下，通过顶层模式切换提供与现有离线选片页面完全独立的**实时伴随模式**。浏览器端采用固定滑动窗口（默认 2 分钟，可配置 1–5 分钟）的流畅低规格**实时伴随代理**展示实时增长的时间轴与枪声检测，同时通过只读**录像监听目录**自动发现任意录屏软件（NVIDIA/OBS/AMD/Steam）新落盘的高画质**原录像**，经由「墙钟粗对齐 + 局部声纹包络互相关精对齐」完成**原片升格**，按需无缝切入现有离线复核与导出管线。

## 背景与问题

现有主线架构（纯静态宿主 `serve.py` + 浏览器本地 Mediabunny / ONNX WASM 引擎）面向定长离线录像设计，`review-workspace.mjs`、`audio-peaks.mjs` 与 `media-read-source.mjs` 均强依赖文件总时长已知且大小恒定。

若希望用户在游戏录像进行中实时看到音频波形、代理画面与枪声候选增长，并衔接至本地高画质原录像精剪导出，面临四重架构张力：
1. **保持纯静态离线与跨录屏软件通用**：不能依赖后端服务器，也不应锁死在单一录屏软件（如 OBS）的私有控制协议上；
2. **内存与游戏同机性能边界**：浏览器无法缓存数小时的实时视频流，且不能在游戏与本地 4K60 录屏并发时引入不可控的内存膨胀或后台整片重扫；
3. **代理画面与高画质原录像的职责冲突**：浏览器采集的限时低规格代理画面与本地录屏软件落盘的高画质原录像处于不同坐标系（绝对墙钟时间 vs 原片相对时间），且画质与完整性不可混为一谈；
4. **导航与状态耦合风险**：离线模式已有分析、复核、导出三页与读写型输出目录授权，强行并入同一套导航和状态容器会破坏既有不变量并引发导出成片被监听目录反吸等故障。

## 决策

1. **顶层完全独立的双工作区模式**
   - 在左上角品牌/工作区标识位置（`Apex Local Cut · 本地选片工作区`）提供模式切换，切换进入完全独立的**实时伴随模式**页面，不改动既有「分析队列 / 片段复核 / 导出任务」三页结构；
   - 实时伴随模式独立管理其会话状态、推理 Worker 与只读**录像监听目录**权限，与离线模式的读写**输出目录**彻底隔离；同时底层仍显式过滤本会话导出队列刚写入的成片文件名，防止两目录被设为同一路径时发生自循环；
   - 实时监听开启期间默认暂停后台离线分析队列，避免与游戏和本地录屏叠加争抢 CPU。

2. **严格隔离「实时伴随代理」与「原录像」，禁止代理直接导出**
   - **实时伴随代理**仅承担实时画面/音频监控、近期滑动窗口回看与轻量**实时预决策**（手动打点、排除误报），**禁止直接提交导出批次**；
   - V1 版本默认优先流畅回看体验：采用浏览器端限时流畅代理视频缓冲（默认 `720p @ 30fps`，约 `2.5 Mbps`，`2s` 分片/关键帧，滚动窗口默认 2 分钟、可配 1–5 分钟，设 150 MB 内存硬上限），切入游戏后台时保活代理写入与音频推理、仅暂停前台 UI 重绘，并在过载时自动提示降档至零编码开销的省电胶片档（实时 `<video>` 直出 + 历史 2fps 关键帧缩略图 + 完整音频环）。

3. **后台静默原片升格 + 按需无缝衔接**
   - 超过滑动窗口后仅淘汰代理视频重资产，轻量历史（20ms 音频能量包络、枪声预测分数、实时预决策）滚动保留 60 分钟且不因单次升格销毁；
   - 连续触发「即时回放」产生时间重叠的多份原录像时，每份新文件各自按覆盖的时间区间独立切片映射；
   - 目录监听确认新原录像落盘稳定并完成对齐后，仅在后台静默升格并高亮提示「原片已就绪」，绝不强行抢焦点跳转；用户主动点击精剪/导出时，才保持时间位置无缝切换至离线工作区复核页，通过轻量 `importPrecomputed` 路径复用现有播放器与导出引擎，并迁移保留实时预决策。

4. **两阶段对齐与三级透明降级（绝不伪造高精度）**
   - 第一阶段通过 `file.lastModified - video.duration` 计算墙钟粗对齐锚点，缩小搜索范围至 ±8 秒；
   - 第二阶段仅用 Mediabunny 局部跳读原录像 15–30 秒音频（长录像抽片头+片尾双锚点消除晶振漂移），与常驻的实时 20ms 能量包络做归一化互相关（NCC），实现 ±20–50ms 级精对齐；
   - 对齐结果按三级透明暴露：① 高置信度标为「精确对齐」直接免重扫复核；② 墙钟重合但声纹低置信度降级为「粗略对齐」（依托现有前后 5 秒 padding 兜底）并提供「一键重新离线分析」；③ 墙钟超出实时会话范围的历史文件忽略不绑，且绝不在游戏后台自动启动全片离线分析。

5. **目标平台与防回环门控**
   - 以 Windows 桌面 Chrome/Edge 为第一目标平台，默认以 `getDisplayMedia`（选整个屏幕 + 共享系统音频）作为零配置入口，并行提供 `getUserMedia`（虚拟声卡 / OBS Audio Monitor）作为纯净游戏音轨隔离与 macOS 兜底入口；
   - 默认启用自动音频回环门控：当页面内任意播放器处于非静音播放状态时自动暂停实时推理与代理写入，防止网页播出的枪声自激形成假阳性死循环（仅 `getUserMedia` 独立音轨允许关闭）。

## 被拒绝的替代方案

- **强绑定 OBS WebSocket 作为唯一主路线**：会排除 NVIDIA ShadowPlay、AMD ReLive 与 Steam 后台录制用户；且 obs-websocket 本身不传输原始 PCM 音频流，仍需浏览器音频采集，还需放宽静态托管 CSP 允许连接本机 WebSocket 端口。未来仍可作为可选增强插件接入，但不作为核心依赖。
- **浏览器定时尾读录屏软件正在写入的视频文件**：与现有 Mediabunny 定长解析假设冲突，普通 MP4 停录前缺少 `moov` 索引无法解码，且在 Windows 下面临文件写锁与截断时长风险。
- **V1 默认采用 2fps 静态缩略图胶片作为唯一回看形式**：虽可做到零视频编码开销，但牺牲了最近 2 分钟的流畅视觉回看亮点；因此改为 V1 默认流畅代理视频，同时保留 2fps 胶片作为低配机降级档位。
- **允许直接导出浏览器 720p 代理流**：会违背 [CONTEXT.md](../../CONTEXT.md) 对「原录像」与「成片」的画质与来源边界，造成用户误导。

## 影响与边界

- **现有架构零破坏**：现有 `review-workspace.mjs` 的定长不变量、`export-queue.mjs` 与 `serve.py` 的严格安全头均可原样保留；仅需在 `browser-analysis.mjs` / `analysis-queue.mjs` 增设 `importPrecomputed` 轻量接入点（跳过 `analyze()`，仅跑 `prepare()` 获取容器与轨道元数据）。
- **设计细化**：完整模块划分、状态机、对齐算法与 PoC 验收标准见 [实时伴随分析与原片升格设计方案](../design/live-companion-analysis.md)。
