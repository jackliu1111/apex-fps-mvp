### 三项复现的具体条件

1. 默认 64 MiB（67108864 字节）预算，两批不同范围均显式指定 1920×1080、15 秒，各模拟生成 20000000 字节；每批估算 53093536 字节。第二批使第一批 `available=false/url=null`，虽然实际合计只有 40000000 字节。释放发生在第二批编码前，第二批失败也不会恢复旧链接。未指定输出尺寸时估算默认用 4K，不能把原片为 1080p 当作估算已获知尺寸；相同参数命中复用、目录输出不走同一淘汰路径。
2. 模拟编码抛出 `ORIGINAL_ENCODER_FAILURE`，删除半成品抛出 `CLEANUP_FAILURE`，最终调用方只得到清理失败信息。
3. 模拟 writer.close 成功时触发取消，观察到 `closed → removed → AbortError`；风险限于当前片成功关闭至完成检查、登记之间。

3b 的根因还包括两层保存语义不一致：队列在 `export-queue.mjs` 中已有 `if (!result.saved) job.controller.signal.throwIfAborted()`，允许取消后仍登记已保存结果；但转换器返回前就因取消抛错并删除文件，队列无法收到 `saved=true`。修复必须同时核对转换器的关闭/清理/返回结果，以及队列的取消/发布/汇总状态。

## 已确定的修改范围（尚未实施）

- 统一目录导出，关闭普通下载链接入口；正常流程不再保留完整 Blob 等待下载，也不再淘汰未保存成片。
- 首次选择输出目录，当前页面后续提交沿用。提交时固定该批来源、范围、声音、设置及实际选定目的地；更换后续默认目录不改写既有批次的保存记录。
- 没有目录或目录权限不可用时等待选择；不退回内存下载。不支持相关能力时明确提示，不自动降低输出规格。
- 文件成功关闭后保留成果并释放处理资源；任务记录与磁盘复用索引可独立保留，索引清理不删除文件。
- 取消仅停止尚未完成工作；未完成文件尝试清理，失败时同时呈现主错误、清理错误与遗留文件位置。
- 目录唯一保存路径落地后，删除 `app.js` 离页判断中的下载遗留条件 `output.available && !output.saved`，不再为已关闭的下载入口保留保存确认机制。
- 同步修改界面和使用说明：根 README 的“小批次提供下载链接，大批次写入目录”、浏览器使用指南的流程及缓存说明、`index.html/app.js` 的 `export-budget`（64 MiB）呈现，以及 `app.js` 中“成片已生成”等完成文案，统一为真实的保存状态。此为实现时必做清单；代码未改前，当前使用说明继续如实描述旧行为。
- 离页提醒的导出条件使用等待目录、排队、运行中的状态。已失败、已取消、已保存的记录不单独触发导出提醒；不顺带删除未提交人工选片的提醒。
- 补第 1、2、3 条的回归测试和真实浏览器目录写入验证。原有测试通过不替代新语义的验收。

## 待验证的实施细节

以下属于实现时必须解决或验证的事项，不表示已做出新的产品承诺：

- 成功关闭后若取消或附加媒体检查失败，如何同时显示“文件已保存”和“检查未完成/失败”，避免显示为未保存或删除文件。
- `export-queue.mjs` 的 `cancel()` 目前立即把运行中的当前片和批次设为 `cancelled` 并通知界面。按新规则，关闭操作仍可能随后成功，造成先显示“已取消”、后显示“已完成”的终态反转。需要区分“请求取消”与“取消已完成”，待当前写入结果确定后发布终态；是否引入取消中状态及其文案仍属实施细节。
- 取消发生在最后一个文件关闭后的批次汇总：逐片结果必须保留，批次标题如何准确表达需要随 UI 实现验证；不能只改转换器而保留队列过早发布终态的行为。
- 目录权限在批次中途失效后，如何保留已完成结果、让剩余片段继续；再次选择不同目录时如何显示实际保存位置，是否需要逐片目的地记录。
- 原 64 MiB 成片缓存预算与 128 项复用索引限制如何拆开：写盘缓冲需要独立边界，不能机械删除所有内存限制。
- 保存成功仅表示写入操作已成功关闭，不等于逐帧正确性、画质、文件永久存在或系统断电后的持久性保证。

最低验收场景：首次选择目录和取消选择；后续批次沿用；权限失效；不支持目录能力；正常保存；写入中取消；关闭成功时取消（包括取消请求发出时 close 仍在进行的竞态，并观察完整状态通知序列）；编码失败且清理成功/失败；多片部分完成；终态批次不误触发离页提示；未提交选片保护仍有效；真实浏览器中读回生成文件。以上均未在本次文档任务中执行。
