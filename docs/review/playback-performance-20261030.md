## 方法与结果

临时脚本通过产品 importFiles/openReview/player 接口驱动真实模块。在测试浏览器内包裹公开 workspace 方法记录执行耗时，不改变方法行为；用CDP CPU采样（2ms间隔）、requestAnimationFrame间隔、Long Tasks与每100ms播放器实际画面时间抽样。每次正式播放前 seek 至300秒并等待1.2秒。

`setReview`耗时包含同步生成工作区视图及 onChange 引起的当前页渲染，不是纯状态存储耗时。CPU采样的调用树包含子调用，不能相加当作总耗时；浏览器原生解码/GPU成本也不由JS采样完整覆盖。rAF间隔不是视频真实丢帧率，播放器 framesDisplayed 也不是屏幕合成帧数。

| 场景 | 秒数 | setReview均值 / P95（ms） | 抽样画面最大滞后（ms） | 最大rAF间隔（ms） | ≥50ms长任务数 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1录像，无候选 | 15 | 1.18 / 1.92 | 16.33 | 100.00 | 1 |
| 1录像，历史28候选 | 15 | 2.45 / 3.24 | 13.00 | 16.67 | 0 |
| 3录像，当前28候选、其余0 | 15 | 2.04 / 2.99 | 16.67 | 16.67 | 0 |
| 3录像，各300压力候选 | 15 | 15.74 / 18.65 | 13.00 | 33.34 | 0 |
| 3录像，各300压力候选（重复） | 15 | 16.66 / 19.80 | 16.67 | 33.34 | 0 |
| 3录像，恢复当前28、其余0 | 15 | 2.58 / 3.11 | 12.67 | 16.67 | 0 |
| 3录像，实际分析与播放并行 | 20 | 0.43 / 0.50 | 15.67 | 16.67 | 0 |
| 当前28，其余各300 | 15 | 3.04 / 4.30 | 15.67 | 99.99 | 1 |
| 当前300，其余0 | 15 | 15.75 / 18.45 | 16.67 | 33.34 | 0 |
| 当前300，预测轴缩到19个可见 | 15 | 4.60 / 6.37 | 16.67 | 16.67 | 0 |
| 当前300，恢复全片视野 | 15 | 14.78 / 19.14 | 16.67 | 33.34 | 0 |

共11段、170秒的播放观察，不是整片播放验收。所有观察段均无页面异常、播放器错误或持续500ms的帧计数停滞；视频时间持续推进，抽样画面滞后均不超过约16.7ms。稀疏抽样不能排除采样间的短暂抖动。

两个独立浏览器会话的首次播放各有一次约116–117ms长任务，CPU采样落在 `createAudioContext/play` 初始化路径；后续重复播放未出现该长任务。这与300候选场景持续出现约33ms的rAF间隔应分开解释，不据此声称冷启动根因已被完整隔离。

初次打开300秒位置约653.8ms；暂停状态跳转至2100秒约511.3ms、900秒约644.0ms、再回到300秒约168.1ms。目标与显示帧时间均相符。每点仅一次且受缓存与存储影响，不将这些值当作稳定P95；也没有检验播放中跳转或快速拖拽。

## 归因证据

1. **可见候选比未查看录像的候选更影响开销。** 当前28、其余各300，setReview均值约3.04ms；当前300、其余空，约15.75ms。三份各300重复约15.74/16.66ms，恢复当前28后降至2.58ms。
2. **保持相同300个候选，仅缩小预测轴视野，更新降至4.60ms；恢复全片视野回到14.78ms。** 缩放用现有“放大”按钮四次；可见候选由300变19，候选列表仍保留300条。这是行为不变的UI条件对照，没有修改源码或屏蔽业务回调。
3. **CPU采样指向时间轴候选循环。** 当前300、其余空的15秒段，`selection-timeline.mjs:180 render`包容采样约2233ms，其中`:226`候选循环约1937ms；主工作区`:46 getSource`明显更小。该时间轴还由播放状态约每100ms更新，不只受0.25秒工作区写回驱动。
4. **代码存在重复线性查找。** `selection-timeline.mjs:226–227` 对每个可见候选重新展开 `predictions.children` 并 find；全片视野下形成近似二次扫描，再逐项写样式、文本、属性及事件处理器。当前页播放位置变化也走这条完整渲染路径。
5. **一次工作区写回可能同时引起两次时间轴渲染。** `app.js:55` 的 onState 先 setReview，经 render/renderReview/renderPlayer 更新时间轴；随后 onState 再调用 renderPlayer。即使移出工作区，独立的播放状态回调仍会更新候选轴，因此不应只修状态存放位置。

额外微基准使用相同真实录像身份和时长，在独立 workspace 实例中只执行公开 setReview（onChange为空，但 view 仍生成），各60次：

| 工作区规模 | 均值（ms） | 最大（ms） |
| --- | ---: | ---: |
| 3份 × 28候选 | 0.081 | 0.350 |
| 3份 × 100候选 | 0.224 | 0.420 |
| 3份 × 300候选 | 0.621 | 0.715 |

这个热循环只说明无DOM时的视图生成量级，不等于从端到端时长中精确减去的成本，也没有模拟复杂人工决定/批次。
