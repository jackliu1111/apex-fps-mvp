# interval-v1 为什么变慢：实测追查

日期：2026-09-16。范围：macOS、同一 496.65 秒 4K60 H.264 录像和 FFmpeg 7.1.1。本轮只做诊断与隔离实验，`typescript/src/` 未修改；没有打包、发布或 Windows 验证。

主要原因是：端点不可读使大部分录像仍需补查，而每次稀疏跳转又重复解码关键帧后的前缀。输出给 HUD 的帧变少，底层解码工作并未按同样比例减少。HUD 多尺度匹配还存在可复现的模板缓存反复淘汰。

## 1. 先拆清原来多出的 63.8 秒

下面沿用[验收报告](interval-v1-validation.md)中最终版本新旧各两次完整分析的均值，没有用本轮带埋点的时间替换原基准。

| 完整 4K 录像 | 旧方案 | interval-v1 | 变化 |
| --- | ---: | ---: | ---: |
| 完整分析 | 215.59 秒 | 279.42 秒 | +63.83 秒 |
| HUD 定位与数字识别 | 162.46 秒 | 116.84 秒 | −45.62 秒 |
| 其余经过时间（总耗时减 HUD） | 53.13 秒 | 162.58 秒 | +109.45 秒 |

“其余经过时间”含取帧等待、进程/管道处理、文件校验等，不能直接当作 FFmpeg 纯 CPU 时间。解码与 HUD 处理可以重叠，阶段列与子步骤列不能重复相加。

新方案稀疏阶段平均 114.29 秒，补查 161.94 秒，文件校验 3.06 秒。候选生成约 1 毫秒。文件校验、候选合并和尾部索引均不是这次回退的主要来源。稳定段也呈同样结构：HUD 省了 13.96 秒，其余经过时间增加 16.98 秒，最终慢了 3.02 秒。

## 2. 稀疏输出不等于稀疏解码

FFmpeg 输入端 `-ss` 先跳到目标之前的可寻址位置，再解码并丢弃到目标时间。裁剪、`select` 和 RGB 转换是解码之后的过滤步骤；减少输出帧或裁剪 HUD，不能据此认为 H.264 解码器也只处理这些像素或帧。[FFmpeg 官方说明](https://ffmpeg.org/ffmpeg.html#Main-options)、[解码与过滤流程](https://ffmpeg.org/ffmpeg.html#Detailed-description)

包索引显示原片有 29,798 个视频包、133 个关键帧；相邻关键帧平均间隔 3.744 秒，最大 4.167 秒。101 次探测到前一个关键帧的间隔平均为 1.981 秒，累计约 200 秒。这些前缀会在不同请求中反复处理。

本轮完整诊断使用源码副本，保留实际识别，记录每个请求的 FFmpeg 解码统计：

| 阶段 | FFmpeg 请求 | 输出帧 | 实际解码帧 |
| --- | ---: | ---: | ---: |
| 稀疏探测 | 101 | 202 | 13,167 |
| 异常补查 | 5 | 4,233 | 25,568 |
| 合计 | 106 | 4,435 | 38,735 |

即每次“取两帧”平均解码约 130 帧。新方案解码总数甚至高于原片一遍的 29,798 帧。这里比较的是原片一遍，并非声称测得旧程序的精确解码总数；旧程序切换 HUD 裁剪时也有一次重启和前缀重复。

诊断中，稀疏请求首帧等待累计 117.88 秒，实际消费者处理累计 31.65 秒，最后一帧后的等待累计 2.06 秒。主要时间在首帧到来之前及识别中，不在进程退出之后。

带埋点全流程本次耗时 390.96 秒，受埋点和未控制后台负载影响，明显不同于之前基准，因此仅用于定位工作量和本次耗时分布，不能用来改写性能回退百分比。探测结果、窗口、读数、事件、候选与最终版本基准逐项一致。

## 3. 未知端点把方案变成“探测一遍，再补查大部分”

- 101 个端点中，仅 24 个获得双帧一致有效读数，77 个未知。
- 100 个原始窗口中，67 个两端未知、18 个单端未知；共 85 个异常窗口。
- 这些窗口已正确合并为 5 段，补查 421.65 秒，占全片 **84.90%**。
- 最长补查为 0–335 秒，因此异常合并虽然减少启动次数，却不能消除这 335 秒的连续工作。

稀疏阶段总共 202 帧，84 帧成功定位 HUD，其中 52 帧数字可读；补查阶段 4,233 帧，1,416 帧定位成功、1,052 帧数字可读。定位失败比单纯数字不可读更多，但本轮没有把所有失败人工细分为 HUD 实际消失、遮挡、尺度或定位错误，不能承诺提高识别率就能消除大部分补查。

稳定段只有 2 个未知端点，也触发其前后共 4 个异常窗口，即 20 秒补查，占 57.968 秒的 34.50%。未知端点会同时影响左右窗口，这是规则的直接结果。

## 4. HUD 多尺度重定位与缓存问题

这段缓存逻辑在旧方案中也存在。本轮没有测出新旧方案的缓存未命中次数差异，因此它是已确认的现有优化点，不能单独作为算法切换后变慢的因果证据。

诊断中，补查定位累计约 118.59 秒，其中 103 次多尺度搜索占 81.43 秒，约 68.7%。降低采样率并不会让这些昂贵的恢复操作等比例消失。

相关路径为 [`HudLocator.refine/search`](../src/core/damage.ts) → [`Matcher.scores`](../src/core/image.ts)。多尺度搜索最多尝试 13 个尺度、2 张图标；较大的局部搜索使用 512×512 的复数 FFT，每张模板变换占 4 MiB，26 张共 104 MiB。现有模板变换缓存上限为 32,000,000 字节，此情形只能保留其中 7 张。按同一顺序循环匹配时，新写入的模板不断淘汰即将再次需要的模板。

做了固定纹理区域的隔离对照：仅将副本缓存上限改为 128,000,000 字节，其余匹配逻辑不变。每个进程重复同一搜索 8 次，按“原版→实验版→实验版→原版”运行，排除每进程第一次冷缓存调用后：

| 局部控制 | 32 MB 上限 | 128 MB 上限 |
| --- | ---: | ---: |
| 每进程缓存查找 | 208 | 208 |
| 每进程未命中 | 208 | 26 |
| 每进程淘汰 | 201 | 0 |
| 热身后平均搜索耗时 | 274.42 毫秒 | 156.56 毫秒 |
| 匹配位置、尺度与分数 | 两组完全一致 | 两组完全一致 |

局部耗时下降约 43%。这是固定搜索区域的微基准，**不是全片提速结果**。真实录像有不同尺寸、尺度及缓存竞争，直接扩大缓存也会增加内存；应先验证按尺寸/模板集合管理缓存，或有界扩大容量，再做全流程输出一致性与交错性能测试。生产缓存尚未修改。

## 5. 实验排除了哪些简单办法

短请求使用录像的 10、125、315、440、490 秒，固定原分辨率裁剪，输出相邻两帧；每点每方案运行两次，第二次反转方案次序，不运行 HUD 识别：

| FFmpeg 设置 | 10 次请求平均耗时 |
| --- | ---: |
| 默认线程 | 1.273 秒 |
| 解码线程改为 2 | 2.194 秒 |
| 过滤线程改为 1 | 1.764 秒 |
| 解码 2、过滤 1 | 2.104 秒 |

各方案在同一时间点的 RGB SHA-256 和 PTS 完全一致。`ffmpeg -version` 的 5 次平均耗时仅 0.072 秒，但这只代表轻量启动对照，不包含媒体初始化，不能把它与真实请求的差值全部归因于寻址。当前样本没有支持减少线程的证据。

另测两段补查，在输入端额外加 `-t`，与现有 `trim` 输出的 RGB/PTS 一致，解码帧数接近；现有请求最后一帧后的总等待很短，排除“trim 后仍解码到片尾”作为主要原因。4 次默认/有输入时限控制的均值为 5.94/5.37 秒，样本小且时段不同，不据此认定稳定优化。

还试了单次连续解码全片、仅输出相同 202 个 PTS 的控制。固定裁剪、不执行 HUD，完整首轮耗时 205.90 秒，解码 29,798 帧。它减少了进程启动，却增加了稀疏阶段本身的解码工作；当前实现未显示优势，因此主动取消第二轮。该实验预先使用已知 PTS，选择表达式也与生产不同，只用于否定“把启动次数减到一次就必然更快”的假设，不是可直接替换的调度实现。

## 建议顺序

1. **先验证模板变换缓存优化。** 已定位到可重复的计算浪费，局部匹配输出保持一致，不需要改变 5 秒/10 FPS 规则。仍需全片验证后再采用。
2. **再拆查未知端点。** 优先区分真正无 HUD 和有 HUD 但定位/数字失败；只有后一类的识别改善才有机会降低补查比例。不能通过把未知当零来换取速度。
3. **保留随机跳转并研究重复工作。** 评估复用解码状态或合理的短批次，但别直接改成全片连续稀疏扫描。当前录像的关键帧间隔和补查比例决定了收益，需保留精确 PTS、相邻帧与证据一致性验证。

即便缓存优化有效，也不能保证抵消全部 63.8 秒回退。5 秒探测策略更适合多数端点稳定可读、补查占比低的素材；当前异常 4K 样本不满足这一前提。
