# interval-v1：5 秒探测与异常补查

新建伤害任务固定使用此策略，不提供旧算法切换。音频流程不变。此次没有打包或发布。

## 处理顺序

1. 文件校验与媒体信息：保留 SHA-256 校验与文件变更检查。
2. 稀疏探测：建立 `0, 5, 10, …, duration`，每点取相邻两张原始帧。两帧均有效且数值一致才接受。尾部以包 PTS 定位最后两个视频帧，不依赖标称 FPS 推算最后帧。取帧使用输入端 `-ss` 和 `-copyts -start_at_zero`；时间来自 FFmpeg 输出的原录像时间戳。视频短到不足两帧时端点未知。
3. 窗口判断：有效端点上升选中整窗，相等跳过，下降或未知进入补查。上升净增量仅是端点差，不创建精确事件。
4. 异常补查：相邻异常窗先合并；每段一个顺序 FFmpeg 请求，以 10 FPS 的时间格选取真实源帧，低帧率/VFR 不补造重复帧。每段新建定位与计数追踪器，附近可靠锚点只提示位置。读取边界确认帧，事件按首次读到新值的时间归入唯一原始窗。未知或下降均断开基线；连续两次同值才确认。只补查这一轮。
5. 候选生成：高亮窗按 `gap_s` 合并，然后加前后缓冲；缓冲后重叠再合并并裁剪边界。尾窗不足 5 秒先向前补足，整片不足 5 秒保留可用全长。

FFmpeg 请求串行，RGB 帧逐个消费，完整录像不进帧缓存。首次定位用全图，后续请求优先使用原分辨率 HUD 裁剪。每段补查期间供帧区域固定；HUD 超出该区域时保持未知，不再递归扩大或重复补查。

## 结果字段

| 字段 | 含义 |
| --- | --- |
| `damage_strategy` | 新结果固定为 `interval-v1`；缺失则按旧结果查看 |
| `damage_parameters` | 5 秒探测、10 FPS 补查及本次合并/缓冲参数 |
| `damageProbes` | 请求时间、实际帧时间、双帧确认值、可靠锚点 |
| `damageWindows` | 原始窗口、探测端点值/净变化、是否高亮、来源与异常原因 |
| `damageWindows.confirmed_increase` | 该补查窗口实际确认增长的合计；与端点净变化分开 |
| `readings` | 实际识别读数；`source=probe/dense`，未知为 `null` |
| `damageEvents` | 仅连续补查确认的事件，不含端点推断 |
| `clips[].window_count` | 当前候选合并了多少个高亮原始窗；不是命中次数 |
| `stats` | 阶段/HUD/文件校验耗时、补查比例、输出帧数、管道字节数、FFmpeg 次数 |

补查范围内的稀疏读数被实际补查证据替代，最终读数按原录像时间排序去重；完整探测历史仍保留在 `damageProbes`。双帧探测端点与补查确认增长是两种证据，补查发现增长但端点不可用时，端点净变化仍显示未知。

曲线用虚线表示区间线性估算，实线表示补查实际读数，未知与计数下降断线。详情列出窗口范围、端点净变化和补查确认增长。旧设置的 `sampling_fps` 被忽略，其他时间设置保留；历史任务文件不迁移、不改写。

## 代码入口

- [media.ts](../src/media.ts)：原录像时间轴上的短窗口取帧、尾部索引、取消与子进程清理。
- [interval-analysis.ts](../src/interval-analysis.ts)：稀疏探测、顺序补查、证据及统计。
- [core/interval.ts](../src/core/interval.ts)：窗口判断、异常合并、事件归属、候选生成。
- [core/damage-curve.ts](../src/core/damage-curve.ts)：新旧结果的曲线几何；不在未知区间连线。
- [shared.ts](../src/shared.ts)：结果与设置接口。

## 已接受的近似

相等端点会跳过内部，窗口内发生增长又重置、短暂显示或识别错误可能不被发现。10 FPS 也可能错过持续不足两个采样的值。旧算法增长位置不是人工真值；对照覆盖率需要与画面抽查一起解读。此方案不保证比连续 30 FPS 更快，随机跳转、异常占比与 HUD 定位成本都会影响总耗时。

功能与性能验收见 [interval-v1-validation.md](interval-v1-validation.md)。
