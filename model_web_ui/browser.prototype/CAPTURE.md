# 纯网页原型的验证记录

日期：2026-10-26。原型分支：`codex/prototype-browser-local`，基于 `2ac7c6f`。

问题：现有 BEATs 模型能否在纯网页里，与本地媒体读取、音轨选择、复核和导出连成可操作的流程？

结论：**短合成样本的真实链路已在 macOS Chrome 跑通**。页面未调用 Python 推理、系统 FFmpeg 或本地媒体服务。Python 只在开发阶段生成 ONNX 和提供静态文件；本机 FFmpeg 仅用于对浏览器已下载的成片进行独立检查。后续真实 4K 长录像性能实测见文末；尚未评价 Apex 识别质量或确定生产架构。

## 已观察的证据

- ONNX 固定输入 `[1,160000]`、输出 `[1,250,447]`。合成噪声与原 PyTorch 分数相比，Python ONNX Runtime 最大绝对误差 `7.82310962677002e-7`。
- Chrome 内点击基准校验：111,750 个分数，最大绝对误差 `7.674098014831543e-7`，通过 `1e-3` 阈值。这是单个合成输入的数值对照。
- 浏览器内部生成双音轨 WebM；原型显示两条独立音轨，未选择时禁止分析。音轨一是合成脉冲，音轨二是 440 Hz 正弦音。
- 分别选轨分析成功：12 秒音频产生 2 个重叠窗口、300 帧分数。默认 0.2 阈值无枪声候选，未伪造识别结果。阈值置零后可重算出覆盖全段的候选，再恢复 0.2 并使用手动范围验证导出。
- 第一音轨手动范围 `1.2–4.8 s` 生成了可播放预览；下载文件 `browser-synthetic-01.webm` 为 171,351 字节，VP8 640×360 + 单条 Opus 音轨，容器时长 3.633 秒，FFmpeg 完整解码成功。
- 修订版为合成视频补充 12 fps 轨道元数据，源视频读回为约 12 秒。第二音轨手动范围 `0–5 s` 下载文件 `browser-synthetic-track2-01.webm` 为 214,665 字节，VP8 640×360 + 单条 Opus 音轨，ffprobe 容器时长 5.000 秒，完整解码成功。解码音频的前 1 秒 FFT 峰值为 440 Hz，符合所选音轨。
- 已观察取消状态：0 完成窗口、0 分数帧、无候选；重新分析后 2 窗口／300 帧完成。失败或取消不会伪装为完成。
- 切换音轨后旧分数和候选清空；修订版同时清空旧预览。已下载链接保留并在新导出文件名中标明音轨序号。
- 使用 Chrome 原生文件选择器重新导入第二音轨成片成功，作为另一份录像加入队列并要求重新确认音轨。
- 通过实际页面截图检查了预览、范围编辑、下载链接和操作导览布局。没有增加自动化测试套件；JavaScript 语法、Python 语法和源码空白检查通过。

## 尚未证明的内容

- 已完成下文单份真实 4K 长录像分析；未验证多文件完整批处理、所有格式、负起点轨道、人工感知同步、后台运行与刷新恢复。

## 2026-10-26 19:24 浏览器耗时实测

用户请求测量耗时。环境为 Apple M6、16 GiB 内存、Chrome 155.0.8059.85，ONNX Runtime Web 1.23.2，WASM CPU 单线程；没有使用 WebGPU。用 `performance.now()` 在 Worker 内分别计时文件读取、引擎初始化、模型执行；主页面统计调用往返、解码及完整流程耗时。

模型冷／热各执行 3 次，以下模型项目为中位数。每次冷会话重新创建 Worker 和 session，但不清理操作系统磁盘缓存；文件通过本机 HTTP 提供且响应为 no-store。热会话复用最后一个 session。每次输出均与固定 Python 基准进行 `1e-3` 最大绝对误差检查，6 次均通过，否则测试不会进入媒体阶段。

## 2026-10-27 EfficientAT mn04_as 小模型构建与浏览器实测

问题：现成蒸馏小模型能否缩短纯网页原型的迭代与处理时间？本轮选用 EfficientAT mn04_as，983,599 参数，未自行训练、量化或剪枝。作者源码固定 a425fdce92572e602a1d5634799bd9f1f2efa806，官方 checkpoint SHA-256 为 899a8c6217063f6941793102a2780b3dd788ab11fce468d9cf5f0577c453321c。出处及权重下载地址保存在 model.json，重建命令见 README。

结论：**小模型真实网页链路跑通，完整录像耗时明显降低；识别质量尚不能视为与 BEATs 等价。** 前端默认小模型，可切回 BEATs；切换会清空旧分数、范围、计时与基准状态。依旧本地 File + WebCodecs / Web Audio + WASM 单线程，无上传或后台模型 API。

模型输入为 32 kHz 单声道的 10 秒窗口、5 秒步长。JS 在 Worker 内实现与作者 eval 前端相同的 preemphasis、reflect padding、Hann STFT、Kaldi Mel 与 log normalization，再把 `[1,1,128,1000]` 输入 ONNX CNN。窗口输出 527 类，保留枪声和机枪声两个概率，显式携带 start/end。窗口级分数不伪装成 BEATs 的 40 ms 帧分数。前处理常量由作者 Python 前端导出，避免使用大型实数 DFT 矩阵。

### 数值与操作验证

- 固定噪声输入：原 PyTorch → Python ONNX 最大分数误差 1.1920928955078125e-7。
- 同一输入：JavaScript FFT/Mel 与 Python 128,000 个前端特征最大误差 0.000010371208190917969；JS 前端 → Python ONNX 最大分数误差 7.748604e-7。
- **Chrome 内完整 JS 前端 + ORT Web WASM** 与原 PyTorch 527 个分数最大误差 3.7997961044311523e-7；冷／热各 3 次全部通过 1e-3 阈值。
- 合成短片链路成功：12 秒、2 窗口，冷会话 0.289 秒，复用会话 0.139 秒；无候选时仍可手动范围导出。
- 实际切换到 BEATs，旧识别结果清空；其浏览器基准仍通过，111,750 分数最大误差 7.674098014831543e-7。
- 完整分析与短片导出由实际 Chrome UI 操作完成；没有通过 Node 测量冒充浏览器结果。Node 仅额外验证 FFT/Mel 数值及 WASM 模型可执行。
